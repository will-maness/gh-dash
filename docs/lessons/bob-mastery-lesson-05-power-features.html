Power Features: The Developer Workflow Toolkit

Bob ships with a set of developer workflow features that go far beyond chat. Rollback, literate coding, code reviews, Bob tips, context mentions, agent steering, and auto-approve together form a complete developer experience. Understanding them deeply is the difference between using 20% of Bob's capability and 80%.

Section 1 of 4

Rollback, Bob tips, and literate coding

↩
Rollback
Automatic version snapshots during AI tasks

Bob captures snapshots of your project's state using a shadow Git repository, separate from your main version control system. Snapshots are recorded when tasks begin and before file modifications — they are not automatically created before running commands. This happens silently in the background.

Each snapshot gives you two operations: View diff (compare current workspace to that snapshot) and Restore. Restore has two sub-options: restore only the files (keeps your conversation intact) or restore everything including conversation history.

The key distinction from a normal git checkout: restoring files without restoring the conversation lets you compare two AI-generated implementations side-by-side while maintaining the chat context. This is valuable when you want Bob to try an alternative approach without losing the context of why it made the first attempt.

Nested Git repos disable rollback: If Bob detects nested Git repositories in your workspace, rollback is disabled with a notification. Remove or relocate nested repos to re-enable it.

💡
Bob tips
Continuous static analysis with AI-powered refactoring

Bob tips runs continuously in the background, calculating code quality metrics at the function level across all open files. It detects two specific categories of problems:

High cyclomatic complexity: Functions with deeply nested conditionals, excessive branching, or too many independent execution paths — the kind of code that becomes untestable and unmaintainable as it grows.

Low maintainability: Functions that are hard to read, test, or extend — often a result of mixed concerns, long parameter lists, or missing abstraction.

When a threshold is exceeded, Bob underlines the function in purple in the editor and adds it to the Bob Findings panel. Clicking Fix with Bob opens a chat conversation with full context about the issue, letting you discuss the refactoring approach before committing to it.

✍
Literate coding
Natural language instructions written directly in source files

Literate coding is a fundamentally different interaction model from chat. Instead of describing a change in the chat panel and having Bob infer the location, you write the natural language instruction directly in the source file at the exact line where the code should go — as a comment, pseudocode, or plain description.

Instructions appear highlighted in blue to distinguish them from real code. When you run Generate, Bob reads the instruction in context (with full visibility of the surrounding code) and produces an inline diff, previewing the implementation right where you wrote the instruction.

This is particularly valuable for targeted changes: adding retry logic to a specific function, inserting a validation block at a specific point, or expanding a stub. The precision eliminates the "Bob changed the wrong place" problem entirely.

⟳
Agent steering & message queue
Redirect a running agent without canceling it

Agent steering lets you send a new message to Bob while it is still executing — you don't have to wait for it to finish, and you don't have to cancel the current task. New messages join a queue that persists even across webview reloads. Bob works through queued messages as soon as it finishes each step.

This changes the interaction model for long-running tasks. Instead of watching Bob execute 15 tool calls and then responding, you can queue up your follow-on instruction as soon as you see where it's headed — or redirect it mid-flight if it's going the wrong direction.

Drag to reorder: Messages in the queue can be dragged to change their execution order. If you realize a later message should run before an earlier one, you reorder without canceling either.

When to use it: Long scaffolding tasks where you want to set context for the next step while the current step is still running. Research or multi-file exploration where you want to queue follow-up questions as Bob's intermediate findings appear.

👁
Preview file edits before accepting
Inspect proposed changes in-editor before committing to them

When this setting is enabled (Settings → Editor → Preview edits), Bob's proposed file changes open as a diff view directly in the editor before you accept them. You see a side-by-side or inline diff of exactly what will change — unchanged lines, deletions, additions — in the same editor you use for all other diffs.

This is distinct from the chat panel's tool-call approval prompt. The approval prompt tells you that Bob wants to write a file. The editor preview shows you exactly what will be written before you commit to it.

Practical use: Enable this for any session where Bob is making structural changes to existing files (refactors, configuration updates, schema migrations). Keep it off for greenfield sessions where Bob is creating new files from scratch — the diff view adds overhead that isn't useful when there's no baseline to compare against.

Task history retention

Bob automatically deletes completed tasks after 14 days to keep your task list manageable. After this period, the task and its conversation history are permanently removed and cannot be recovered. You can change this in Settings → Chat → Task retention. Setting the value to 0 disables automatic deletion. Task history is stored locally — not backed up or synced across devices.

PM Insight

Bob tips, rollback, agent steering, and edit preview together address the four most common developer fears about AI-assisted code: "will it silently degrade quality?", "what if it breaks something I can't undo?", "what if it goes in the wrong direction?", and "what exactly will it change?". Each feature is zero-setup and always-on (or one toggle away). The product value proposition here is trust at scale: developers who can observe, redirect, and preview AI actions are willing to delegate larger and more consequential tasks.

Context mentions: the @ system explained

Context mentions let you inject specific project content directly into a prompt without copying and pasting. You type @ in the chat input and select what to reference. Bob receives the exact content of whatever you mention — not a description of it.

Syntax What it injects Key detail
@/path/to/file.ts Full contents of a specific file Bypasses .bobignore — useful for explicitly sharing generated or ignored files
@/path/to/folder Contents of all files directly in that folder Non-recursive — does not include subfolders. Watch context window size with large directories.
@problems All diagnostics from the Problems panel Lets Bob see every current TypeScript error, lint warning, etc. in one shot
@terminal Current terminal output / last command result Ideal for "why did this fail?" — Bob sees the actual error output directly
@git-changes Current staged/unstaged diff Perfect for pre-commit review: "review @git-changes before I commit"
@https://… Fetched and Markdown-converted web page content Uses headless browser; strips navigation/scripts. Good for referencing docs.
Context mentions in action — power combinations
Example 1 — Multi-file review
"Fix @problems in @/src/components and explain what was wrong"

Bob receives the full diagnostics list AND the complete contents of every file in /src/components in a single prompt. No file exploration needed — everything is already in context.

Example 2 — Debugging with terminal output
"The build is failing. Here's the output: @terminal — what's wrong and how do I fix it?"

Bob sees the exact terminal output, not a paraphrase. This is far more reliable than copy-pasting error text, which often loses formatting and truncates stack traces.

Example 3 — Pre-commit review
"Review @git-changes and check against the API spec at @https://api.mycompany.com/docs"

Bob compares your actual uncommitted diff against live documentation pulled from the URL. This is impossible to do in a standard chat interface without significant manual preparation.

Context window trap

Mentioning a large folder or a heavily-referenced file injects all that content into the context window immediately, and it stays there for the rest of the conversation. @/src on a large project could consume tens of thousands of tokens before you've typed a single word of your actual question. Be surgical: mention the specific files or the specific folder, not the entire project root.

Section 3 of 4

Code reviews, commit messages & PR generation

🔍
Code reviews (/review)
AI-powered diff analysis before you commit

Trigger with /review in the chat panel. Bob opens a dedicated Review panel where you select a branch to compare against. It analyzes the diff between branches and populates the Bob Findings panel with flagged issues.

Critically: reviews run with auto-approval enabled — Bob proceeds through all analysis steps without asking for confirmation at each tool call. This is by design; the review workflow is read-only, so the safety risk of auto-approval is low and the speed benefit is high.

You can optionally attach a GitHub issue to validate that your changes actually address its requirements — Bob cross-references the issue description against the diff.

✉
Commit messages & PR generation
Consistent, meaningful git history without the manual work

Bob generates commit messages by examining staged changes, branch name, and recent commit history to determine the correct format. It follows conventional commit standards (feat:, fix:, refactor:, etc.) and derives the scope and description from what was actually changed — not from what you tell it to say.

PR generation works similarly: Bob analyzes the full diff between your branch and the base, creates a structured description, and fills in any template sections your repo defines. Clear section headings in PR templates (## Summary, ## Changes) dramatically improve output quality.

Both features are designed to be reviewed before use — not auto-submitted. Bob drafts; you approve, edit, and submit.

Why this matters for PM

Commit message quality is a hidden product health signal. Repos with AI-generated commit messages that follow consistent conventions become significantly easier to audit, changelog-generate from, and search through. PR descriptions that reference the issue being addressed create a traceable link from requirement to code to deployment. These aren't glamorous features, but they're compounding value — the ROI shows up months later when someone needs to understand why a change was made.

Section 4 of 4

Auto-approve settings: the security tradeoff matrix

Auto-approve controls whether Bob needs your explicit confirmation before executing each action. By default, every tool call requires approval. You can selectively enable auto-approve for specific action categories — and each toggle carries a different risk profile.

Low risk
Read operations (read_file, glob, grep)
Safe to auto-approve for almost all users. Reads are non-destructive. The only risk is context window cost from large reads, not data integrity.
Caution
Write operations (apply_diff, write_file)
Acceptable for experienced users with rollback enabled. Risk: Bob could write to an unintended file. Rollback mitigates this, but you lose the opportunity to catch mistakes before they happen.
Higher risk
Execute operations (execute_command)
Auto-approving execute allows Bob to run shell commands without review. A misunderstood request could result in rm -rf, package installs that modify lockfiles, or environment state changes. Only enable for very well-scoped workflows where you trust the command patterns Bob will generate.
Caution
MCP operations
Risk depends entirely on what the MCP server can do. Auto-approving MCP for a read-only search server is low risk. Auto-approving MCP for a server that can send Slack messages or create Jira tickets is a different story entirely.
Low risk
Skills
Auto-approving skills means Bob activates specialized workflows without asking. Generally safe — skills only inject instructions, they don't execute anything on their own.
The correct default posture

Start with everything requiring approval, then selectively enable auto-approve for the categories you've confirmed are safe for your workflow. The docs explicitly state: "configure these settings based on your risk tolerance and workflow needs." There is no universal "right" setting — it depends on the task, the team, and the MCP servers in use. Re-evaluate auto-approve settings when adding new MCP servers or starting a new project type.

Bobcoins: the billing model you need to understand cold

Bobcoins are the unified billing metric Bob uses instead of raw tokens. The reason: different underlying AI models consume tokens at vastly different rates and costs. If IBM billed in tokens, switching from one model to another would make cost unpredictable from the user's perspective. Bobcoins abstract over that complexity — you set a Bobcoin budget, and the conversion to tokens happens automatically, invisibly.

Think of it this way: tokens are to Bobcoins what kWh are to dollars on your electricity bill. The underlying unit exists; you just don't manage it directly.

Verify current pricing

The Bobcoin allocations above reflect plan tiers at time of writing. IBM may update these at any time. Always verify current allocations at bob.ibm.com/pricing before quoting them in customer conversations or procurement planning.

The two biggest Bobcoin levers users control are: conversation length (every prompt re-sends the entire context — long threads are expensive) and file reads (every file Bob loads persists in context for the conversation's duration). These are structural cost drivers, not usage bugs — they're a consequence of how LLMs work.

Overage nuance

Overage allows you to pay for Bobcoins beyond your monthly allocation at a per-unit rate. It applies to Pro, Pro+, and Ultra plans — but specifically not to Free Trial or Enterprise plans. For Enterprise, you buy additional packs in bulk from IBM Sales rather than using a metered overage system. Know which regime applies to your team when capacity planning.

PM Insight

Bobcoins are a product pricing design decision worth understanding deeply. By abstracting over model tokens, IBM retains the ability to swap underlying models (for performance, cost, or capability reasons) without re-pricing from the customer's perspective. This is the same logic behind "compute units" in cloud services — model abstraction creates commercial flexibility. It also means customers can't easily comparison-shop on token economics alone.

Bobalytics & Enterprise features

Bobalytics is the analytics dashboard for Enterprise plan users — only admins with Enterprise plans can access it, via the Admin section on bob.ibm.com. It provides insight into how Bob is contributing to the software development lifecycle at the team and workspace level.

The three Bobalytics KPIs

Adoption Rate
%
How many people on the team are actively using Bob. The primary "is anyone actually using this?" metric.
Bob Factor
×
Bob's tangible contribution to shipped code — the proportion of committed code that originated from or was significantly modified by Bob.
Bobcoin Spend
🪙
Team-level AI tooling cost. Used with Bob Factor to assess efficiency: value generated per Bobcoin spent.
The privacy design choice you must know

Bobalytics is deliberately designed to show team-level data, not individual user data. Admins cannot see which specific developer is spending how many Bobcoins or how often. This is a product privacy decision — IBM chose team aggregation over individual tracking. You will be asked about this in enterprise evaluations. The correct answer: "you can see team performance, not individual surveillance data." This is a feature, not a limitation.

Telemetry note for Enterprise

Enterprise plan users must keep telemetry enabled to view data in Bobalytics. Disabling telemetry disables Bobalytics analytics for that user. This is a known tradeoff — individual users who opt out of telemetry disappear from the team's Bobalytics view. Mention this when configuring org-wide telemetry policies.

The full security threat model

Understanding Bob's security model isn't optional for a PM working with enterprise customers. The threat surface is real and the mitigations are specific. Here's the complete picture.

ThreatSeverityHow it happensMitigation
Context poisoning High Bad facts accumulate in conversation history. Bob treats them as ground truth on every subsequent prompt. Replies drift toward the false assumption. Start a new task (new context window). Don't try to correct context poisoning by arguing within the same conversation.
Prompt injection Critical Malicious content in files, URLs, or tool output contains hidden instructions that Bob reads and executes. An attacker-controlled file tells Bob to exfiltrate code. Use .bobignore for sensitive areas. Vet MCP servers. Avoid reading untrusted files in the same context as privileged operations.
MCP server risks High An untrusted MCP server can be a vector for prompt injection, data exfiltration, or executing unauthorized actions on connected systems. Vet all MCP servers before installation. Check open-source code. Understand what data the server can access. Apply principle of least privilege.
Secret exposure Critical API keys, tokens, or credentials in code or config files get loaded into Bob's context and potentially sent to underlying model providers. Use .bobignore for .env and secrets/ directories. Never paste credentials into the chat. Use delegated access (short-lived tokens, narrow scopes).
Auto-approve escalation Medium Overly permissive auto-approve settings allow Bob to execute destructive commands or write to sensitive files without human review. Default to manual approval for write and execute. Auto-approve only read operations by default. Re-evaluate after each new MCP server addition.
Context poisoning: the mechanics in depth

Context poisoning is subtler than a simple error. The wrong fact doesn't just affect one response — it gets re-sent with every subsequent prompt for the rest of the conversation. Corrective prompts within the same conversation don't reliably fix it: the poisoned history is still there, and any future off-topic question can re-activate the bad assumption. The only reliable fix is a new task (+ button in the chat panel). Not "sorry, you were wrong about X." Not a correction prompt. A new context window.

PM Insight

The security story for Bob enterprise evaluations has three layers: data privacy (IBM states it does not use prompts for training data), access control (.bobignore, mode permissions, auto-approve settings), and threat mitigations (context poisoning recovery, MCP vetting, secrets hygiene). Enterprise buyers will ask about all three. Know the specific product mechanisms — not just "Bob is secure" — because that's what security review panels actually probe.

Scaling Bob: Shell, API keys & team deployment patterns

Bob Shell

Bob Shell is the command-line interface for Bob — it runs in a terminal instead of the IDE extension. It has all the same capabilities as the IDE version but is more appropriate for: CI/CD pipelines, server environments without a GUI, automation scripts, developers who prefer terminal-first workflows, and remote SSH sessions.

Authentication in Bob Shell uses API keys rather than the interactive IBMid login flow. Two types are available:

API Key TypeScopeWhen to use
General Scoped to a subscription instance; usable across multiple services. Requires Team ID header for inference requests. Shared team automation, CI/CD pipelines where multiple services need access
Inference Scoped to a specific subscription instance and team; limited to inference requests only. No additional headers required. Simpler automation setups, single-team pipelines, lower-privilege scenarios
API key security

Never hardcode API keys in configuration files or scripts. Store them as environment variables or in a secrets manager. Add any file containing API keys to .gitignore and .bobignore. Exposed API keys in a repository are a real incident, not just a policy violation — they can be used to consume your Bobcoin budget or access your Bob instance.

Team deployment patterns

There are three common patterns for rolling out Bob across an engineering organization, each with different tradeoff profiles:

  • 1. Bottom-up adoption: Individual developers install and use Bob at their discretion. Low friction, fast time-to-value, but inconsistent practices and no team-level Bobalytics visibility.
  • 2. Repository-first standardization: Teams commit AGENTS.md, .bob/skills/, .bobignore, and custom_modes.yaml to the repo. Any developer who clones the repo gets the team's Bob configuration automatically. High consistency, lower friction than policy mandates.
  • 3. Enterprise governance: Central IT deploys Bob with org-level telemetry policies, Enterprise plan Bobcoin pools managed by team leads, Bobalytics for leadership reporting, and vetted MCP servers pre-approved for org use. Highest control, most governance overhead.
Recommended starting point

Pattern 2 (repository-first standardization) gives the best ROI for most teams starting out. It's lightweight (just files in the repo), immediately benefits all team members who clone the project, and creates the foundation for Pattern 3 enterprise governance later. Start by committing a focused AGENTS.md with your team's core coding conventions, then add skills as the team identifies repeating workflows.

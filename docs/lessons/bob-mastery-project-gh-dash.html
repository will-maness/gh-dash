Before you begin

How this guide works

Each session maps to one lesson. Read the lesson first, pass the quiz, then open this guide for that session. The exercise only makes sense after you understand the concept — if you try to follow the steps without the lesson context, you'll be going through motions instead of building intuition.

Three rules that hold for every session:

1
One Bob conversation per session. Start a new conversation at the beginning of each session. Don't carry a conversation over from the previous one. The codebase persists; the context does not. This is intentional — it exercises context discipline from Lesson 1.
2
Honor the constraint for each session. Each session has a red "constraint" box listing things you cannot do yet. The constraint is what makes it an exercise. Skipping it means you're not practicing the lesson's mechanic.
3
The prompts are starting points, not scripts. The prompts shown are what to send Bob to initiate each step. Bob's response will vary. You'll need to approve tool calls, iterate, and make judgment calls. That's the point.
Prerequisites

You need: Node.js 18+ installed, a GitHub account, and a GitHub Personal Access Token (classic, repo scope) stored as an environment variable. You do not need to set up the token before Session 1 — that happens in Session 4. Sessions 1–3 use Bob's own GitHub MCP connection or public API endpoints that don't require auth.

Step 1 — Send the scaffold prompt

Open a new Agent mode conversation and send this single prompt. Then stop. Read every tool call approval before clicking approve.

Send this prompt Agent mode
"Scaffold a Node.js project called gh-dash. It will eventually analyze GitHub repositories and produce health metrics. For now, create: a src/ directory with a github.js module that exports a stub fetchRepo(owner, repo) function using the GitHub REST API v3; a src/metrics.js module with stub functions prCycleTime(prs) and commitFrequency(commits) that return null; a cli.js entry point that accepts --owner and --repo flags and logs 'Fetching {owner}/{repo}...'; and a public/index.html dashboard shell with placeholder cards for PR Cycle Time, Commit Frequency, Stale Branches, and Contributors. Add a .gitignore for node_modules and .env. Do not install any npm packages yet."
While Bob works — observe these things
  • How many tool calls does Bob make before writing a single file?
  • Does Bob read anything before it writes? What does it read and why?
  • How many separate write operations does it use — one big write or surgical per-file operations?
  • Does it verify anything after writing?
  • After 3–4 tool calls, notice the approval prompt getting longer. That's context accumulating.

Step 2 — Verify the structure

After Bob finishes, send one verification prompt:

Verification prompt Agent mode
"List the files you created and confirm each one has the correct exports or structure."

Watch what tools Bob uses to answer this. Does it re-read the files it just wrote, or does it answer from memory? Notice whether re-reading files generates more tool calls — and understand that each of those reads is now in your context window for the rest of the conversation.

Step 3 — Make one observation note

Before closing this session, open a new file in the project manually (not via Bob) and write a short note. This becomes your learning log for the project.

Create this file yourself — not via Bob
LEARNING_LOG.md — write: "Session 1: I observed N tool calls. Bob read [X] before writing. The context window had [describe what you noticed]. One thing that surprised me: [your observation]."

Bob made multiple decisions you didn't specify: file structure, naming conventions, how to parse CLI flags, how to structure the HTML. Each of those decisions became a fact in the context window. The right response would have been to start a new conversation with a more precise prompt. Keep that in mind for Session 2.

Constraints for this session

Phase 1 — Plan mode: design before building

Start a new conversation in Plan mode. Do not open Agent mode yet.

Plan prompt — send this first Plan mode
"I need to implement PR cycle time analysis in gh-dash. Cycle time = the average duration in hours from a PR's created_at to its merged_at, across all merged PRs in a repo. Using the GitHub REST API v3 (GET /repos/{owner}/{repo}/pulls?state=closed), design the implementation plan. Show me: which files need to change, what the fetchPRs function signature should look like, the algorithm for the prCycleTime calculation, how the result gets written to the dashboard HTML, and any edge cases I should handle. Do not write any code yet."

Read Bob's plan carefully. Look for anything that conflicts with the structure from Session 1 — wrong file names, different function signatures than what exists, assumptions about how the HTML is structured. Correct any mistakes now, before a single line of code is written. This is the entire point of Plan mode.

What to look for in the plan
  • Does the plan reference the actual filenames from Session 1, or does it invent new ones?
  • Does it account for the edge case where merged_at is null (PR was closed but not merged)?
  • Does it specify how the result flows from metrics.js to the HTML — or leave that vague?
  • Does Plan mode try to write any files? (It should not — that would be a mode violation.)

Phase 2 — Agent mode: implement the plan

Switch to Agent mode. Start a new conversation — do not continue the Plan conversation.

Implementation prompt Agent mode
"Implement PR cycle time analysis in gh-dash based on this plan: [paste the key points from the plan Bob just produced]. Specifically: update src/github.js to add a fetchPRs(owner, repo) function that calls GET /repos/{owner}/{repo}/pulls?state=closed&per_page=100; update the prCycleTime(prs) function in src/metrics.js to compute average hours from created_at to merged_at, skipping PRs where merged_at is null; update cli.js to fetch PRs and log the cycle time result; update the PR Cycle Time card in public/index.html to display the computed value. Run node cli.js --owner facebook --repo react to verify it executes without errors."

Watch each write approval carefully. Verify that Bob is editing the files from Session 1, not creating new ones. If it tries to restructure the project, decline the tool call and correct the prompt.

Phase 3 — Ask mode: audit the implementation

Switch to Ask mode. Start a new conversation.

Audit prompt Ask mode
"Review src/metrics.js and src/github.js. Does prCycleTime correctly handle the case where a PR has no merged_at? Is there a risk of dividing by zero if all PRs are unmerged? Does fetchPRs handle GitHub API pagination — what happens with repos that have more than 100 PRs?"

Bob will identify any gaps. Note them in LEARNING_LOG.md. You are not fixing them now — just recording. The deliberate use of Ask mode after Agent mode is the practice: build, then audit without side effects.

Session 2 deliverables
  • src/github.js — fetchPRs function added
  • src/metrics.js — prCycleTime implemented with null guard
  • cli.js — logs PR cycle time for a given repo
  • public/index.html — PR Cycle Time card populated
  • LEARNING_LOG.md — note on what the Ask audit found
What you just practiced

You used three modes for three distinct mental postures in a single feature. Plan mode forced you to catch design errors before they became code errors. Agent mode executed without needing to re-explain the design. Ask mode audited without risk of accidentally changing something. This three-phase pattern — Plan → Agent → Ask — is the highest-leverage workflow for complex features. You'll use it instinctively by Session 5.

Constraints for this session

  • The multi-repo fetch must use parallel subagents — do not write a sequential loop
  • The skill must be in .bob/skills/ (project-scoped), not your global skills directory

Part A — Write your gh-analysis skill

Create the skill file manually before this session's Bob conversation. This is deliberate — writing the skill yourself forces you to think about what domain knowledge is actually worth encoding.

Create the directory and file: .bob/skills/gh-analysis/SKILL.md

Write the following content:

--- name: gh-analysis description: Analyze GitHub repositories for health metrics including PR cycle time, commit frequency, stale branches, and contributor activity. Use when writing or extending analysis functions in gh-dash that call the GitHub REST API v3. --- # gh-analysis Skill ## Domain conventions in this project All GitHub API calls go through `src/github.js`. Never call the API directly from metrics.js or cli.js. Metric functions live in `src/metrics.js` and accept raw API response arrays as their only argument. They return a single number or null. The dashboard renders metric values by ID: `#pr-cycle-time`, `#commit-freq`, `#stale-branches`, `#contributors`. ## GitHub API patterns PRs: GET /repos/{owner}/{repo}/pulls?state=closed&per_page=100 Commits: GET /repos/{owner}/{repo}/commits?per_page=100 Branches: GET /repos/{owner}/{repo}/branches?per_page=100 Contributors: GET /repos/{owner}/{repo}/contributors?per_page=100 All endpoints paginate. Check the Link header for rel="next". ## Key edge cases to always handle - merged_at is null for closed-but-unmerged PRs — skip these for cycle time - Branches with no commits in 90+ days are stale - The default branch is never stale regardless of commit date - contributor.login may be null for deleted GitHub accounts

Part B — Build the multi-repo comparison feature

Now open a new Agent mode conversation. Bob should detect and activate the skill automatically when your request is relevant to GitHub analysis.

Send this prompt Agent mode
"I need to extend gh-dash to analyze multiple repos simultaneously and compare their PR cycle times side by side. The repos to compare are: facebook/react, vercel/next.js, expressjs/express, axios/axios, and lodash/lodash. The analysis for each repo should be run in parallel — use subagents so the main conversation context doesn't get polluted with five separate sets of API calls. Each subagent should fetch that repo's closed PRs and return a summary object: { repo, avgCycleTimeHours, totalMergedPRs }. After all five complete, render a comparison table in public/index.html showing all five repos ranked by cycle time."
Watch for these specific mechanics
  • Does Bob activate the gh-analysis skill? It should — the request matches the description.
  • How many subagents does Bob spawn? It should be 5 (one per repo), running in parallel.
  • What comes back to the main conversation from each subagent — the full tool trace or just a summary?
  • Does Bob set fork_context: true on the subagents? Would it need to here? (Think about what each subagent needs to know.)

After this completes, do a quick sanity check — the comparison table should show real cycle time data for at least 3 of the 5 repos (some may return errors if their APIs behave differently at query time).

Session 3 deliverables
  • .bob/skills/gh-analysis/SKILL.md — hand-written skill file committed to the repo
  • src/github.js — updated with multi-repo fetch capability
  • src/metrics.js — consistent with skill conventions
  • public/index.html — comparison table with 5-repo results
  • LEARNING_LOG.md — note on whether Bob activated the skill automatically, and what the subagent summaries looked like vs. what a sequential approach would have produced
What you just practiced

The skill did two things simultaneously: it gave Bob domain vocabulary (the ID conventions, the file architecture, the edge cases) and it constrained Bob's behavior (always route API calls through github.js). Without the skill, Bob would have had to infer these from reading your code — at token cost, with risk of getting them wrong. With the skill, the knowledge was already in context before Bob looked at a single file. That's the compounding value of a well-written skill: every future session in this project benefits from it automatically.

Part A — Write AGENTS.md by hand

Create AGENTS.md in the project root manually. This is your team contract — writing it yourself is more valuable than having Bob generate it, because you have to consciously decide what matters.

Minimum contents to include:

# gh-dash — Bob Configuration ## Architecture rules All GitHub API calls must go through src/github.js. Metric calculation functions live in src/metrics.js only. The dashboard is a single HTML file at public/index.html. Do not create additional HTML files or a build step. ## Code style Use CommonJS (require/module.exports), not ES modules. Function names use camelCase. Files use kebab-case. No external dependencies beyond node-fetch. ## Error handling All GitHub API calls must handle 404 (repo not found) and 403 (rate limited) responses explicitly. Never throw uncaught errors.

Part B — Create .bobignore

Create .bobignore in the project root:

Part C — Create the custom repo-analyst mode

Create .bob/custom_modes.yaml:

customModes: - slug: repo-analyst name: 📊 Repo Analyst description: Extends gh-dash with new metrics and analysis features. roleDefinition: You are a developer extending a GitHub repository analytics tool. You understand the GitHub REST API v3, JavaScript metrics computation, and HTML dashboard rendering. whenToUse: Use for any task that adds or modifies analysis features in gh-dash. customInstructions: Always check AGENTS.md before making architectural decisions. No new dependencies. groups: - read - - edit fileRegex: "^(src/|public/|cli\\.js|AGENTS\\.md)" description: Source and dashboard files only - execute - skill - mcp

Part D — Wire up the GitHub MCP server

Open Bob Settings and add the GitHub MCP server. This gives Bob real GitHub API access using your personal token — no more stub functions needed.

In Bob Settings → MCP Servers, add this configuration
Server name: github
Transport: STDIO
Command: npx -y @modelcontextprotocol/server-github
Environment: GITHUB_PERSONAL_ACCESS_TOKEN = [your token from .env]

Part E — Verify the configuration with a live fetch

Switch to the custom repo-analyst mode and start a new conversation:

Verification prompt repo-analyst mode
"Using the GitHub MCP server, fetch the 10 most recent merged PRs for vercel/next.js and compute the average cycle time in hours. Then update src/github.js to replace the stub fetchPRs function with a real implementation that uses the MCP server's list_pull_requests tool instead of a raw HTTP call."
Watch for these specific mechanics
  • Does the repo-analyst mode prevent Bob from editing any file outside src/ or public/? Try asking it to edit package.json — it should decline.
  • Does Bob reference AGENTS.md when making architectural decisions?
  • Does the MCP server provide richer data than the raw HTTP stub? Compare the response structure.
  • Is your .env file visible to Bob? Run a glob for .env — it should return nothing.

Part A — Add the metrics stub via chat

Start a new conversation in repo-analyst mode.

Setup prompt repo-analyst mode
"Add a contributorTrends(commits) function stub to src/metrics.js. It should accept an array of commit objects from the GitHub API and return null for now. Also add a fetchCommits(owner, repo) function to src/github.js that uses the MCP server's list_commits tool. Add a Contributors card to public/index.html with an empty SVG element (id='contributor-sparkline', width='200', height='40')."

Part B — Write the algorithm using literate coding

This is the key step. Do not use the chat panel for this part. Instead, open src/metrics.js directly in the editor.

Find the contributorTrends(commits) stub. On the line after the opening brace, activate literate coding mode and type this instruction directly in the file:

// Group commits by week for the last 12 weeks. For each week, count unique // contributor logins. Return an array of 12 integers in chronological order. // A commit's week is determined by its committer.date field (ISO 8601). // Weeks with no commits should return 0, not be omitted from the array.

Hit Generate. Bob reads the surrounding function signature and your instruction, then produces the implementation as an inline diff. Review the diff before applying — check that it handles the "no commits" weeks correctly.

Compare literate coding to chat
  • Bob knew exactly which function to implement — you didn't need to describe file or function name
  • The generated code is already in the right place — no copy-paste, no "insert after line X"
  • The surrounding context (the function signature, other functions in the file) shaped the output style automatically

Part C — Render the SVG sparkline via chat

Back in the chat panel:

Sparkline prompt repo-analyst mode

Part A — Add stale branch detection

New conversation, repo-analyst mode.

Feature prompt repo-analyst mode
"Implement stale branch detection in gh-dash. A branch is stale if its most recent commit is more than 90 days old and it is not the default branch. A note on what "done" means here

gh-dash is a complete, working tool — but it's not production-ready. Pagination is only partially handled. The dashboard doesn't auto-refresh. Error states aren't styled. The SVG scaling is basic. That's intentional. This is a learning vehicle, not a product. If you want to take it further, you now have the Bob skills to do it properly: write a spec in Plan mode, implement in repo-analyst mode, review before committing. You know the workflow.

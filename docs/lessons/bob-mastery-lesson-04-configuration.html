Configuring Bob: Modes, Rules & MCP

Bob ships with sensible defaults, but the teams that get the most from it are those who invest in configuration. Custom modes, layered rules, and MCP integrations collectively define the difference between using Bob as a generic tool and deploying it as a team-specific AI platform.

Section 1 of 4

Custom modes: building specialized Bob personas

Custom modes let you define purpose-specific Bob configurations with their own role, tool access, file permissions, and behavioral instructions. They're defined in YAML and can be committed to the repo (project-level) or stored globally for personal use.

There are two configuration locations: project-level at .bob/custom_modes.yaml (version-controlled with the repo, available to all team members) and global at ~/.bob/settings/custom_modes.yaml (personal modes available across all projects). You can edit either via the settings menu: Settings → Modes → Edit Project Modes or Edit Global Modes.

Here's a real example — a documentation-writer mode that restricts Bob to only editing Markdown files:

# .bob/custom_modes.yaml (or ~/.bob/settings/custom_modes.yaml for global) customModes: - slug: docs-writer name: 📝 Documentation Writer description: Writes and revises Markdown documentation. roleDefinition: You are a technical writer specializing in clear documentation. whenToUse: Use this mode for writing and editing documentation. customInstructions: Focus on clarity. Use sentence-case headings. groups: - read - - edit fileRegex: "\\.(md|mdx)$" # Edit Markdown ONLY description: Markdown files only - skill

The most important fields to understand:

FieldWhat it controlsKey detail
slug Unique identifier — also used for rule directory names (rules-{slug}/) Letters, numbers, and hyphens only — no spaces. Must be unique. Matching an existing built-in slug overrides that default mode.
roleDefinition Bob's identity and expertise in this mode — injected into the system prompt Write it as "You are a [expert]…" — this shapes Bob's approach and vocabulary.
groups Which tool categories are enabled Available: read, edit, execute, mcp, skill, subagent, subtask, todo, mode. If you omit groups, the mode gets no grouped tools.
fileRegex Restricts edit access to specific file patterns A mode with fileRegex: "\\.md$" literally cannot write to .ts or .py files. Invalid regex prevents the file from loading.
customInstructions Behavioral rules loaded with the mode Combined with any rules-{slug}/ files to form the full instruction set.
allowedSubagents (Optional) Restricts which subagent types the mode can spawn If set, only the listed presets are available. Omit to inherit the default restrictions for the tool groups you've granted.
PM Insight

Custom modes are how you productize Bob for a team. A product-manager mode with fileRegex restricted to *.md files and a roleDefinition focused on user research and requirement writing is genuinely different from what developers get out of the box. Teams that build well-crafted custom modes see measurably better output quality because the mode's role alignment eliminates ambiguity in every request.

The rules hierarchy: how Bob's instructions layer

Bob accumulates behavioral rules from multiple sources, each with a defined precedence. Understanding this hierarchy is essential for debugging unexpected behavior and for building configurations that scale to teams.

1
Mode-specific rules (rules-{slug}/)
Files in .bob/rules-agent/, .bob/rules-plan/, or .bob/rules-{custom}/ — loaded alphabetically, only for that mode
Highest
2
AGENTS.md (workspace root)
Team-standardization file, version-controlled with the project. Loaded after mode-specific rules. Ideal for repository-wide standards.
High
3
General workspace rules (rules/)
Files in .bob/rules/ — apply to all modes in this workspace. Good for project-wide conventions.
Medium
4
Global rules (~/.bob/rules/)
Your personal rules that apply across all projects. Good for individual style preferences.
Lowest

Rules are additive — they stack from lowest to highest, with higher-priority sources able to override lower ones. A project-committed AGENTS.md that says "always use TypeScript strict mode" will override a global rule that says "JavaScript is preferred."

AGENTS.md is the team contract

The AGENTS.md file is designed for team standardization. Commit it to the repo, include it in code review, and treat it as a living document. It's how you make Bob's behavior consistent across a team without each developer needing to configure their own settings. Common uses: coding style standards, documentation requirements, test methodology, architecture constraints.

Important: rules are context window cost

Every rules file loaded into Bob's context consumes tokens on every prompt. A verbose AGENTS.md with 2,000 lines of rules costs those tokens on every single message in every conversation in the project. Rules should be focused and non-redundant. If your team has a 500-line AGENTS.md, audit it — verbose rules are a hidden cost multiplier.

MCP: extending Bob with external tools

The Model Context Protocol (MCP) is a standardized protocol that lets Bob connect to external tools and services. Think of it like USB-C: any MCP-compatible tool can plug into any MCP-compatible AI, without building custom integrations.

MCP client-server architecture
IBM Bob (MCP Client)
Sends tool call requests
⟺
MCP Protocol
STDIO or HTTP/SSE transport
⟺
MCP Server
monday.com, Jira, databases, APIs…

MCP enables Bob to do things the built-in tools cannot — query your Jira backlog, search internal knowledge bases, pull data from product analytics, interact with monday.com boards, or call any custom internal API you've wrapped in an MCP server.

STDIO vs. HTTP transport

ConsiderationSTDIO (Local)Streamable HTTP / SSE
Location Local machine only Local or remote
Security Inherently secure (process isolation) Requires explicit security measures (TLS, auth)
Setup Simpler — just a local process More complex — requires HTTP server
Multi-client Single client only Multiple clients can connect
Best for Individual dev tools, personal integrations Team-shared servers, enterprise integrations
MCP Servers settings panel (no JSON required)

Since Bob 2.0, you can add, configure, and remove MCP servers directly from Settings → MCP Servers — a dedicated tab that gives you a central UI for all connected tools. You no longer need to hand-edit JSON configuration files to register a server. The underlying config format is unchanged if you prefer editing directly, but the settings panel is the canonical entry point for most users.

MCP security questions to ask before adding a server

Before adding any MCP server, especially in a corporate environment: Who built it and is it open-source auditable? What data does it access? Does it store or log prompts? Can it take irreversible actions (delete, send emails)? Is there a published security model? When in doubt, consult your security team — MCP servers extend Bob's security boundary into whatever the server can reach.

Section 4 of 4

.bobignore: controlling what Bob can see

The .bobignore file works like .gitignore — it's a list of patterns for files and directories that Bob's tools should not access. This is your primary mechanism for keeping sensitive files (credentials, secrets, generated outputs) out of Bob's reach.

# .bobignore — common patterns .env .env.* secrets/ *.key config/credentials.json node_modules/ dist/ *.log

When Bob lists files with list_files, ignored files are omitted or marked with a 🔒 symbol. Strict enforcement applies to all read and most write operations — read_file, glob, grep, apply_diff, and write_file all respect .bobignore rules.

Known limitation

.bobignore is not a full sandbox. The insert_content and search_and_replace tools have a known limitation where the final write operation may bypass .bobignore rules due to their internal save mechanism. Also, execute_command protection is limited to a predefined list of file-reading commands — custom scripts may not be blocked. Use .bobignore as defense-in-depth, not as your only access control.

PM Insight

The combination of custom modes + AGENTS.md + .bobignore is the full configuration surface of Bob. Think of it as a three-layer policy system: what Bob acts like (modes), how Bob should behave (rules), and what Bob can see (.bobignore). An enterprise deployment that doesn't configure all three layers is leaving significant governance capability unused.

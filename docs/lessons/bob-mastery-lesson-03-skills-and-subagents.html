Skills & Subagents: Teaching Bob to Specialize

Skills inject specialized knowledge into Bob's context on demand. Subagents let Bob parallelize work in isolated contexts. Together, they're the mechanism by which Bob scales from a general assistant to a domain expert that can tackle complex, multi-threaded work.

Section 1 of 4

Skills: what they are and how they work architecturally

A skill is a Markdown file (SKILL.md) that Bob loads into the context window when a request matches the skill's description. Think of skills as specialized instruction sets — domain-specific knowledge, workflows, checklists, or prompt patterns that you want Bob to apply consistently without having to retype them every session.

Skills don't run automatically at every prompt. Bob reads the description in the skill's YAML frontmatter, decides whether the current request matches it, and then (with your approval, unless auto-approve is enabled) calls use_skill to load the full skill body into context. Once loaded, the skill stays in context for the rest of the conversation — it's a one-time load per session.

The SKILL.md format

Every skill file follows the same structure: YAML frontmatter, then the skill body in plain Markdown.

--- ← YAML frontmatter start name: security-audit description: Audit code for OWASP vulnerabilities, hardcoded secrets, and injection risks. Use when reviewing code for security issues. --- ← YAML frontmatter end # Security Audit Workflow When auditing code, always check in this order: 1. Search for hardcoded credentials with grep patterns 2. Audit all SQL queries for parameterized query usage 3. Check for open redirect vulnerabilities in URL handlers 4. Verify all user inputs are validated before processing 5. Document every finding with severity: Critical / High / Medium / Low

The name field is the identifier used internally. The description is what Bob reads to decide when to activate the skill — write it like a trigger condition, not a title. The body is the actual instructions Bob will follow.

Write descriptions as trigger conditions

The description is Bob's activation decision criteria. "Security audit skill" is a bad description. "Audit code for OWASP vulnerabilities, hardcoded secrets, and injection risks. Use when reviewing code for security issues" is a good one — it tells Bob exactly when to use it. Vague descriptions lead to skills activating at the wrong times or not activating at all.

Skill scoping: global vs. project-level

Skills can live at two locations, and the hierarchy is strict:

~/.bob/skills/ # Global — your personal library └── security-audit/ └── SKILL.md # Available in any project <project>/.bob/skills/ # Project-level — version controlled └── security-audit/ └── SKILL.md # Takes precedence over global

Priority rule: if a skill with the same name exists at both levels, the project-level skill always wins. This lets teams distribute standardized skills via the repo (committed to .bob/skills/) while still allowing individual customization at the global level for personal projects.

Skills can also include supporting files alongside SKILL.md in the skill directory — reference material, examples, checklists — that Bob gains access to when the skill is activated. Keep SKILL.md focused on the core workflow and move bulky reference content to supporting files.

G
Global skills (~/.bob/skills/) Best for: personal workflows, cross-project utilities, individual coding standards you always want applied
P
Project skills (.bob/skills/) Best for: team-wide standards, project-specific domain knowledge, committed to Git so the whole team benefits automatically
PM Insight

Project-level skills committed to the repo are a powerful team consistency mechanism. If your security team writes a security-audit skill and commits it, every developer who uses Bob in that project automatically gets that audit workflow applied — without any manual setup. This is how you scale best practices without enforcement overhead. The skill is the policy.

Subagents vs. subtasks: the critical distinction

Both subagents and subtasks let Bob delegate work, but they serve fundamentally different purposes and have different interaction models. Conflating them is a common mistake.

Subagent Subtask
Visibility Runs silently in the background Appears in the UI with its own breadcrumb and conversation thread
Interaction Not interactive — returns only a summary when done Fully interactive — you can follow along and continue the conversation
Context Own isolated context window (keeps main context clean) Its own conversation thread with independent history
Use case Background information-gathering, isolated side work Complex work that benefits from dedicated tracking and visibility
Tool spawn_subagent start_subtask

The three conditions for spawning a subagent

Bob should only spawn a subagent when all three of these conditions are true simultaneously — not just one or two:

1
The task is clearly self-contained It can be fully described in the spawn instruction without needing back-and-forth. If it needs iteration, use a subtask instead.
2
The result can be summarized back The subagent's output is a summary or a set of findings — not something the parent agent needs to directly integrate or modify.
3
It would add significant irrelevant content to the main context Without a subagent, the exploration work would pollute the parent context with tool calls and intermediate results that aren't needed later.
When NOT to use a subagent

Don't spawn subagents for simple file reads, quick searches, or single-tool operations. The overhead of isolation isn't worth it for tasks that can be done in one or two direct tool calls. Subagent overuse is a cost antipattern — each spawned agent has its own context window overhead.

The fork_context parameter

By default, a subagent does not see the parent conversation history. This is intentional — it keeps the subagent's context lean and focused. But sometimes the subagent needs to understand prior decisions or constraints established earlier in the conversation.

Setting fork_context: true passes the full parent conversation history into the subagent. Use this when the subagent needs to understand prior discussion, decisions, or discovered information — for example, if you spent 10 messages deciding on an architecture and want the subagent to write code consistent with those decisions.

Skill activation + subagent coordination — security audit workflow
Your prompt
"Do a security audit of the payment module and the user auth module in parallel."

Step 1 — Skill activation

use_skill("security-audit") → loads OWASP audit checklist into context

Step 2 — Spawn parallel subagents (both conditions met: self-contained, summaries back)

spawn_subagent("Audit src/payment/ for OWASP vulnerabilities using the security-audit checklist. Return findings with severity ratings.", fork_context: true)
spawn_subagent("Audit src/auth/ for OWASP vulnerabilities using the security-audit checklist. Return findings with severity ratings.", fork_context: true)

Step 3 — Results merged into main conversation

Bob receives both summaries and compiles a unified audit report. All the tool calls the subagents made internally never appear in the main conversation context — only the final summaries do.

Section 4 of 4

Subagent types: explore vs. general

There are two subagent types, and the mode you're in determines which ones Bob is permitted to spawn:

Type Capabilities Available in Best for
explore Read tools, explorer model (lighter, faster) All modes (Agent, Plan, Ask) Codebase exploration, research, gathering information
general Inherits current mode's full tool set Agent mode only Parallel implementation tasks, side work that needs write access

The explore type is deliberately lightweight — it uses a faster model optimized for reading and understanding code without writing anything. Ask and Plan modes are restricted to explore subagents, which reinforces their read-only/no-execute constraints all the way through the delegation chain.

PM Insight

Skills are the primary mechanism for building specialized Bob configurations for different teams. A PM team might commit a product-analysis skill that loads structured frameworks for analyzing feature requests. A DevOps team might have an incident-response skill. The skill system is how organizations make Bob a specialist, not just a generalist. This is a competitive moat if you build a library of high-quality skills before competitors do.

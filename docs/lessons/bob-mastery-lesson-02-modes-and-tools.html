Modes & Tools: Bob's Operating System

The three built-in modes aren't cosmetic — they determine exactly which actions Bob is physically capable of taking. Understanding this permission model is the foundation of using Bob safely and effectively.

Section 1 of 4

Why modes exist — and why they're enforced, not suggested

When you switch modes in Bob, you're not changing Bob's "personality" or tone. You're changing its tool permissions at a hard architectural level. Ask mode literally cannot call apply_diff or execute_command — those tools are not available to it. This isn't a preference; it's a constraint enforced by the mode's permission groups.

This matters enormously in practice. It means that when you put Bob into Ask mode to explore a codebase or audit for security issues, you get a genuine safety guarantee: no accidental file writes, no commands fired, even if Bob misunderstands your intent. You're browsing, not editing.

The three built-in modes are purpose-built for the three mental postures of software development: understanding (Ask), planning (Plan), and executing (Agent). Each one restricts or enables tool groups accordingly.

Mode Primary purpose Read Write Execute Allowed subagents
Agent Implement, fix, build ✓ ✓ ✓ Explore + General
Plan Design, architect, spec ✓ ✓ ✗ Explore only
Ask Understand, explain, audit ✓ ✗ ✗ Explore only
Common misread: Plan mode

Plan mode does have write access. It can write files — specifically for creating spec documents, architecture notes, and planning artifacts. What it cannot do is execute shell commands. So Plan is "read + write docs, no execute," not "read-only." Both Plan and Ask restrict subagent spawning to the explore type — if a spawn isn't permitted by the active mode, Bob completes the work directly without spawning.

PM Insight

This permission model is a direct product design choice that addresses enterprise risk. Many companies are cautious about AI agents that can execute shell commands without human review. The explicit mode separation lets teams enforce a policy: "only senior devs can work in Agent mode; the rest stay in Ask/Plan." That's a real enterprise governance story.

Important

The switch_mode tool is available in all three built-in modes, but Bob should only use it when you explicitly ask or when the current mode genuinely lacks capability needed to finish the task. Modes should not switch spontaneously — that would undermine the permission safety model.

The Plan → Agent workflow: when to use it

The most important mode-switching decision is whether to use Plan → Agent or go straight to Agent. Both are valid. The choice depends on how much uncertainty or complexity you're working with.

Plan mode
Design, spec, decompose
→
Review plan
You approve the approach
→
Agent mode
Execute with full tools

Use Plan first when: the task touches multiple files across the codebase, you're uncertain about the right architecture, the change is risky and you want an explicit written plan to review, or you're onboarding into an unfamiliar project.

Go straight to Agent when: the task is well-scoped (e.g., "fix this specific function"), you already know the approach, or the task is simple enough that a plan would take longer than just doing it.

Ask mode vs. Agent mode — same request, different results
Your prompt (in Ask mode)
"Refactor the authentication module to support OAuth."

Ask mode response:

read_file("auth/auth.ts") → reads the current implementation
grep("OAuth", "src/") → searches for any existing OAuth references

Bob explains the refactoring approach, identifies which files would need to change, and describes the OAuth integration strategy. It does not write any files.

If you then switch to Agent mode and say "do it":

apply_diff("auth/auth.ts") → modifies the auth module
write_file("auth/oauth-provider.ts") → creates new file
execute_command("npm test auth/") → verifies nothing broke
PM Insight

The Plan → Agent pattern maps directly to how well-run engineering teams work: design review before execution. If your team has a code review culture, you can enforce it architecturally by requiring that significant tasks go through Plan mode first. The plan output is a written artifact — commit it, review it in a PR, then execute. This is a real governance workflow, not just a suggestion.

Section 4 of 4

Read tools in depth: how Bob explores a codebase

Read tools are the foundation of everything Bob does. Before writing a single line of code, Bob typically executes several read operations to understand the codebase. Knowing which read tools exist — and what each one is good for — helps you write better prompts and understand why Bob makes the exploratory calls it does.

The pattern Bob follows is: glob to find files → read_file to inspect them → grep to find specific patterns → GetSymbolsOverview or FindSymbol for code-structure-aware navigation. It almost never reads files randomly. It reasons about which files are relevant first.

Why this matters for cost

Every file Bob reads lands in the context window for the rest of the conversation. A read of a 500-line file early in a session means that 500 lines are re-sent with every subsequent prompt. If Bob reads 10 large files while exploring, those reads compound across every message that follows. Being precise about what you ask Bob to look at is a direct cost optimization — not just a style preference.

The GetSymbolsOverview and FindSymbol tools are especially worth understanding. Rather than reading entire files, they extract just the class/function/method structure — the skeleton — at a fraction of the token cost. Bob uses these to "see the shape" of a file before deciding which specific parts to read in full.
